Sudocode Error-Handling Architecture

The "Who-Can-Act" Taxonomy — who can act on this error
design doc · lives in docs/design/error-taxonomy.html · mirrored to ShareOne via remote-url

0In one sentence

An error should not be split into "retryable vs not" — it should be split by who can fix it. That decides what the system does with it.

Transport

the transport layer can fix it
  • 429 / 5xx / 520·522·524·525
  • connect / timeout
  • truncated stream
auto-retry

Model

the LLM can fix it
  • bad tool arguments
  • a request the model built badly
  • context overflow (while compaction budget remains)
llm-revisit — feed back to the model

Human

only a human can fix it
  • auth failure 401/403
  • bad config / missing key
  • request too large
surface to the user

Fatal

nobody can fix it
  • malformed server response
  • unrecoverable internal error
terminal · stop
Transparency is a hard requirement. Sudocode is a hacker tool: every error surfaced to the user must state what failed, which bucket it is, and what the system is doing — e.g. ⟳ retry 3/8 — Cloudflare 524, context window exceeded — compacting and retrying, missing ANTHROPIC_API_KEY. Never a swallowed or generic "something went wrong".

4Three places the taxonomy resists a clean mapping (stated honestly)

Four buckets is the right axis, but reality resists in three spots that the refactor must handle explicitly, not paper over.

① Context-window is state-dependent. It is Model (auto-compact + retry) while compaction budget remains, and only becomes Human once exhausted. The bucket depends on runtime state, so action() must be combined with the compaction budget — the bucket cannot be hard-coded into the error type.
② llm-revisit currently covers only tool errors. Provider errors never take the feed-back-to-model path. Making Model-actionable provider errors go through llm-revisit is Phase 2.
③ Human vs Fatal is not represented today. safe_failure_class is the telemetry/analytics axis, not the "who can act" behavior axis. The two axes are kept separate (SRP); they must not be conflated.

6Guardrails (red lines for the whole refactor)

InfrastructureDo not touch nexus kernel / syscall / raft ABI — this is all in the api/runtime/engine error path, zero infra-ABI surface
PersistenceErrors are ephemeral; nothing here is persisted
DeletionReplaced duplicate fns / markers are removed outright and callers repointed; no "replacement for the retired X" tombstones
Perfaction() is an inline enum match, only on the error path — zero success-path cost
SRP / orthogonalityBehavior axis (ErrorAction) and analytics axis (safe_failure_class) stay separate
TransparencyEvery surfaced error states what/which-bucket/what-the-system-is-doing; never swallow or blur
VerificationEach phase: fmt + clippy clean, live tests (prefer live PTY), full CI green before merge
