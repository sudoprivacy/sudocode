01

三套系统，三种侧重点#

Codex 侧重从历史会话中提炼经验；CC 侧重维护可按需读取的记忆文件；Sudocode 已有文件记忆和存储抽象，但默认会预加载正文，更容易消耗有限上下文。

CODEX CLI

把历史经验
整理成知识库

历史会话提取 → 合并整理 → 注入总摘要 → 按需检索证据。

CLAUDE CODE

先给索引
需要时再读正文

默认按仓库记忆。运行版本还包含受开关控制的自动召回和后台整理。

SUDOCODE

记忆文件
直接参与提示构建

兼具项目与 agent 范围、VFS 抽象；正文加载、预算与维护机制仍需完善。

最重要的纠正：三者都有“记忆文件”，不代表它们注入相同内容、使用相同消息角色，也不代表全局、项目和 worktree 的隔离规则相同。

先把三种“记忆”分开

类别保存什么典型形式与本次调查的关系
固定指令工作规则、仓库约定、用户要求AGENTS.md / CLAUDE.md用于区分范围和注入机制
长期记忆偏好、项目知识、成功与失败经验记忆索引、条目、会话经验摘要本次调查重点
会话恢复 / 压缩某次会话的上下文与进度transcript、resume、compaction独立机制；不会自动等同于长期记忆

能 resume 一个 session，不代表新 session 会自动获得它的知识。会话压缩也不自动等于跨会话知识整理。

04

记忆到底怎样进入 context？#

先看三条实际路径，再比较上下文预算。箭头表示内容的读取与传递，不表示每一步都会新增模型调用。

4.1 Codex · 先给总摘要，再沿索引找证据

  1. 读取 memory_summary.md，对摘要部分施加约 2,500 tokens 上限。
  2. 将摘要与检索指引合成 developer 层提示片段。
  3. 需要细节时，模型搜索 MEMORY.md，再读取相关 rollout_summaries 或经验材料。
  4. 使用记忆时，有文件行号、来源会话等引用约定，便于回溯。

这份总摘要可以包含用户偏好、通用经验、项目内容导航。因此，Codex 注入的内容比单纯的“文件名＋一句介绍”更丰富。

版本读取路径需要注意
V1总摘要 → 搜索 MEMORY.md → 会话摘要 / 经验本地源码的默认版本
V2总摘要 → 直接读取匹配的会话摘要代码已实现；目录与模板独立，由配置决定使用哪一套

源码：[C1] 注入与预算[C2] V1 / V2 读取指引

4.2 CC · 使用规则与记忆内容走不同位置

“独立记忆文件＋简短索引”的理解基本正确，但不能将整个机制笼统称为“把文件列表塞进 system prompt”。此次代码追踪确认：

  • system 中包含如何使用和更新记忆的规则。
  • 索引经自动上下文链加载；instructions → Re(...) 最终构造 role: "user"、带 isMeta 标记的消息。
  • 正文不默认全部展开；模型根据需要读取。
  • 索引有 200 行及额外长度限制。

源码：[A1] 索引与上下文链[A2] meta 消息构造；文档：CC memory

4.3 Sudocode · 构建 system prompt 时就加载正文

Sudocode 会把索引、条目名称、类型、描述，以及截断后的正文一起注入。当前排序没有使用用户问题来判断相关性；条目装不下时直接跳过。

预算项当前实现实际含义
单条正文ENTRY_BODY_CHAR_CAP = 2_000按字符截断，追加截断提示
整体预算RENDERED_CHAR_CAP = 16_000实际判断用 String::len()，单位是 UTF-8 字节
索引先追加原始 MEMORY.md未受这段总预算检查覆盖
取舍依据条目按 name 排序后逐个尝试不等于相关性、重要性或时效性排序

相近的文件格式，不等于相同的注入策略。CC 默认采用索引与按需读取；Sudocode 当前采用正文预加载。

源码：[S1] 渲染与预算[S2] 文件发现、解析与排序

记忆怎样产生、更新和“忘记”？#

5.1 Codex：后台提炼是设计重点

代码不仅生成文件，还管理处理过程：

机制作用
候选会话条件依据空闲时间、年龄与处理数量等限制决定本轮处理哪些历史
任务状态与锁使用数据库任务状态、锁及失败重试协调后台工作
额度检查额度不足时跳过相应处理
使用反馈使用次数、最近使用时间参与候选内容筛选
来源追踪保留来源会话与摘要，使用时可引用文件和行号
根会话边界临时会话、功能关闭或非根 agent 等情况跳过后台启动流程

这使 Codex 适合积累“某个问题以前如何解决、什么尝试失败了”的经验。代价是生成存在时间差，且后台处理需要额外资源。

当前读取指引还规定：当用户明确要求 remember / forget 时，先在 extensions/ad_hoc/notes/ 写追加式更新笔记，由后续流程整理生成的记忆状态。因此，“记住 / 忘记”的请求与生成文件最终更新之间可能存在间隔。

源码：[C3] 显式记忆更新[C4] 后台入口[C5] 筛选与使用反馈

5.2 CC：当前 agent 维护文件，后台能力受开关控制

普通路径中，agent 用文件工具新建、更新、删除记忆，同时维护 MEMORY.md 索引。主要类型为 user / feedback / project / reference。

当前运行版本包含更多能力。是否采用这些路径，需要结合开关和运行环境判断。

可选能力实际代码行为边界
自动召回围绕当前用户问题选择相关记忆，最多 5 个文件存在去重、会话预算、读取范围等约束
模型选择路径让模型从记忆清单中选出相关文件不是普通索引注入的必经步骤
BM25 路径有本地关键词检索索引与相关性筛选实现这条路径是词项检索；不应误称为向量检索
后台提取从近期交互提炼记忆，限制可读写范围含跳过重复工作、合并正在运行任务等条件
Auto Dream按时间、会话数量等条件触发整理与普通 session compaction 是不同机制
展开：本地功能开关观察与代码定位

检查时，本地缓存显示 tengu_moth_copse、tengu_passport_quail 为 false，tengu_onyx_plover 的 enabled 为 false。它们分别与这里讨论的召回 / 提取 / 整理路径有关。

缓存状态不等于对全部运行进程有效配置的证明。环境变量、远程配置和其他存储模式可能影响路径。因而，对当前普通使用体验仍以“索引＋按需读取”为主要解释。

被召回的本地记忆正文也有读取上限，截断时会提示再使用 Read 查看完整内容。

源码：[A3] 召回入口[A4] BM25[A5] 后台提取[A6] Auto Dream

5.3 Sudocode：已有直接维护流程，长期整理仍较薄

当前 agent 获得保存、更新、去重、遗忘等提示，可以使用文件工具维护记忆。默认 memory 链中尚未看到独立的后台会话提取、合并及按使用频率淘汰的流程。

已经实现

  • 记忆条目元数据与正文解析
  • 提示规则引导保存、更新、去重、遗忘
  • 项目与 agent 类型范围
  • 可替换 provider、VFS 文件后端
  • 按会话禁用默认 memory 链

仍需接通或补齐

  • prefetch(query, ctx) 默认返回 None，尚无调用
  • 按当前问题挑选相关记忆
  • 后台会话提取与长期整理
  • 来源、使用反馈与老化策略
  • 损坏条目和加载失败的可见反馈

当前去重、纠错主要依赖模型遵循提示。MemoryProvider 是扩展入口，但接口本身不能视为已经完成的召回系统。

06

全局、项目与 worktree 的边界#

这一部分直接影响“换目录启动后，能否继续记得我们之前的工作”。

场景Codex CLICC 普通 auto memorySudocode 默认 host 路径
同一仓库、不同子目录同一 CODEX_HOME 共享库共享仓库记忆通常共享同一 Git 根派生的目录
同一仓库、不同 worktree仍在同一共享库内默认共享项目记忆通常生成不同记忆目录
不同仓库记忆库仍可共享，内容需判断适用项目项目 auto memory 默认分开默认分开
跨机器共享 CODEX_HOME 的本地设计不等于自动同步普通本地记忆不等于自动同步取决于实际文件后端与 VFS 配置
全局个人层共享摘要可包含用户偏好全局 CLAUDE.md 属于指令；代码另有可选 account memory默认 provider 未体现独立全局个人层

6.1 Codex：共享库，依靠内容和检索判断适用范围

同一 CODEX_HOME 下使用共享记忆目录。此次检查的历史候选查询没有按当前 cwd 隔离。切换 repo 后，仍可能用到此前项目积累的经验。

项目关系主要由内容中的路径、项目说明和模型检索判断维护。共享本地存储不表示已经运行的所有 session 会立即刷新同一份上下文。

6.2 CC：默认仓库范围，额外 scope 需单独判断

默认 auto memory 位于 ~/.claude/projects/<project>/memory/，同一仓库的 worktree 共享。全局 ~/.claude/CLAUDE.md 属于用户指令层。

运行代码还包含 account 范围的 ~/.claude/memory/personal/、team 范围与 connected/shared stores。因此，准确结论是“默认项目记忆＋可选其他范围”，而非“CC 完全没有全局记忆”或“所有普通会话都默认共享全局自动记忆”。

6.3 Sudocode：目录来自工作树根，而非共同仓库身份

默认执行 git rev-parse --show-toplevel，用结果生成目录名。不同 worktree 返回的工作树根不同，通常会得到不同记忆目录。SUDOCODE_MEMORY_DIR 覆盖或 VFS 管理路径可以改变这一点。

子 agent 默认按类型划分 agent-memory/<agent_type>/；这是跨同类 agent 会话的持久范围，不是为每个临时实例单独创建永久记忆。

依据：[C5] cwd 与筛选[A7] CC 路径与范围[S2] Sudocode Git 根[S4] agent 与 VFS；CC 官方范围说明

6.4 对多 repo、多 worktree 工作方式的建议

设计建议 将适用范围作为显式属性，避免把长期经验与临时工作状态混在同一个目录语义里。

范围建议保存示例
用户长期沟通偏好、工作习惯偏好中文说明、先查源码再下结论
仓库稳定项目知识模块关系、测试入口、基础设施约定
worktree / session当前工作状态分支、未完成任务、本地服务端口
agent 类型专门角色可复用的经验某类审查或排障 agent 的检查方法

Sudocode：哪些是 bug，哪些是选择？#

把明确缺陷与设计差异分开，可以避免在行为目标尚未确定时盲目“修复”。以下优先级是本次调查建议。

编号发现性质建议
F-01总预算未覆盖完整索引，字符 / 字节口径混用明确实现缺陷优先修复
F-02条目按名字分配有限上下文加载策略问题增加按需读取与相关性选择
F-03worktree 记忆默认不共享范围语义差异先明确产品目标
F-04/memory 编辑的是指令文件管理能力缺口区分规则与自动记忆管理
F-05解析失败的条目被静默跳过可观察性不足显示加载状态与错误

F-01优先修复总预算没有覆盖索引

触发
MEMORY.md 足够长，或提示前言加索引已超过整体预算。
原因
先完整追加索引；之后只在“是否追加条目”时检查预算。没有条目时还会直接返回。
结果
最终记忆区块可以超过声明的 16,000 上限。
附带问题
整体用 UTF-8 字节计数，单条用字符计数，提示文字却统一称 char。
建议
统一预算口径，并让前言、索引、条目和截断提示都进入预算分配。

确定性：源码静态路径已确认；本次未修改实现、未添加或运行针对该问题的测试。[S1]

F-02按名字决定谁先占用上下文

条目按 name 排序，依次尝试放入预算。随着记忆增加，排序靠前的条目更容易被加载；后面的相关记忆可能被跳过。

判断：这是扩展性问题。先使用短索引与按需读取，再根据实际需求接入相关性召回。[S2]

F-03worktree 范围需要先定语义

如果产品目标是“同一仓库的工作树共享项目经验”，当前路径算法不能满足。当前分支、任务与端口等状态则仍可能需要单独保存。

判断：应先决定哪些内容按仓库共享、哪些按 worktree 隔离，再选择稳定的仓库身份与目录结构。[S2]

F-04/memory 尚不是自动记忆管理入口

当前命令读取 ProjectContext.instruction_files 并打开编辑器；没有指令文件时创建 AGENTS.md。它没有提供自动记忆条目的查看、删除、作用范围和加载状态管理。

建议：界面明确区分“工作规则”和“自动记忆”，让用户看见实际目录与启用状态。[S5]

F-05保存了，却不知道为什么没加载

加载器跳过解析失败的文件，也跳过子目录、隐藏文件、非 Markdown 文件。对解析错误缺少明显反馈，会增加“上次保存过、下次没读到”的排查成本。

建议：提供已加载、预算跳过、格式错误等状态，并给出出错文件的位置。[S2]

建议怎样演进 Sudocode？#

设计建议 优先保证范围与读取行为可预测，再扩大自动化程度。

顺序工作可观察的完成标准带来的收益
1修预算边界与单位长索引、中文、空条目等情形都遵守一致上限控制上下文开销，消除明确实现缺陷
2定义作用范围用户能判断一条记忆属于用户、仓库、worktree 还是 agent减少跨目录丢失或误用
3短索引＋按需读取初始提示保持小而稳定，任务需要时能找到正文避免按名字挤占上下文
4记录来源与更新时间关键记忆可追溯到会话或确认来源，支持纠错与遗忘让记忆可以核验与维护
5接通召回与后台整理按问题选择内容；提取和整理有触发条件、状态与成本约束长期积累经验，降低人工维护成本

从 CODEX 借鉴

来源与维护

会话来源、引用反馈、后台提取及合并整理。

从 CC 借鉴

索引与按需读

文件可读、记忆可编辑，默认加载边界清晰。

保留 SUDOCODE 的基础

Provider 与 VFS

让不同部署环境复用同一记忆接口与范围语义。

后续是否需要 BM25、模型选择或向量检索，应根据记忆数量、查询类型和实际漏召回案例决定。当前最直接的收益来自读取、范围与维护机制的补齐。

当前 Codex 配置状态，也需要单独说明

检查到的全局 config.toml 没有显式开启 features.memories；本地源码默认值为 false。拥有功能，不等于当前实例已启用。这份观察不能代替对启动参数、项目覆盖及宿主配置的完整检查。

源码：[C6] 功能与读取开关；文档：OpenAI 官方 memories 文档

09

留给我们在这里讨论#

下面是尚待决定的设计议题，不是已确认的需求。评论时可引用 Q-01 等编号，或直接针对前面的具体段落讨论。

Q-01 · 仓库记忆是否应跨 worktree 共享？

建议：共享稳定项目知识；将分支、任务、端口等状态保存在 worktree / session 范围。

需要决定：现有分散记忆怎样合并；同一仓库的多个 clone 是否也共享；冲突如何处理。

Q-02 · 默认注入索引，还是继续预加载正文？

建议：默认短索引＋按需读取，有限的自动召回作为后续能力。

需要决定：无工具可用时的降级方式，以及明确要求“必须记住”的高优先级信息是否直接注入。

Q-03 · 全局用户偏好是否需要独立一层？

建议：独立用户范围，并显示每条记忆的作用范围。

需要决定：哪些偏好可跨项目通用；用户规则与 agent 自动推断冲突时怎样更新。

Q-04 · 先修确定缺陷，还是同时调整整体架构？

建议：先处理 F-01 的预算问题与加载诊断，再按确认的范围语义做后续调整。

需要决定：是否保持现有目录兼容，以及迁移和回滚的边界。

Q-05 · 后台记忆什么时候值得开启？

建议：先积累真实漏记、重复排障案例，再设置提取触发条件和成本预算。

需要决定：用户如何查看生成来源、纠正错误记忆，以及“忘记”后怎样避免旧会话再次生成同一条内容。
