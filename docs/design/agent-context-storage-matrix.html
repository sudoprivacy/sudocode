Agent Context / Image / Profile — Unified Storage Matrix

Map Claude Code's on-disk context model onto the given Nexus two-layer design (/agents/{name}/ image + /proc/{pid}/ runtime), and track how sudocode & sudowork store the same things today (for dedup / migration). Draft for consensus — not yet merged into nexus-integration-architecture.

The frame (read first). Nexus's two namespaces are the given end-state, not an open question — same split an OS makes between an executable on disk and a running process (nexus-integration-architecture §2): image layer = /agents/{name}/ (config.toml · prompts/ · skills/ · memory/ — persistent, Metastore, the addressable identity; its sessions/ is a DT_LINK index into the flat /sessions/ store, not the bytes) vs runtime layer = /proc/{pid}/ (status · agent→link · chat-with-me · workspace/ — ephemeral, stamped at start_session, reaped on exit; pid = an ephemeral run handle, not the session id (session-id is the durable layer — Q1)).

Three IDs (nexus Q1, 2026-08): agent-name (durable principal) · session-id (durable UUID, the --resume key, spans many pids) · pid (ephemeral runtime handle). session-id ≠ pid. Sessions are a flat byte-SSOT at /sessions/<session-id> (no workspace_hash, no agent nesting); per-repo & per-agent ties are DT_LINKs + an owner field, isolation by policy not path. This is the distinction from CC/scode, whose primary key is the cwd.

This table's job: put CC's flat ~/.claude/projects/<cwd>/ model on each row, then read across — (1) does the Nexus end-state cover it? (2) how do sudocode & sudowork store it today, and what's dup to merge? CC is the reference we map from; Nexus is the target all three converge to.

This is a working doc (migration burndown), not a snapshot. CC (reference) and the Nexus end-state (target) are fixed; the two current columns — sudocode & sudowork — are live, written as original → what it maps to. As each migration lands, advance that cell + its badge (gap → partial → done); a row is finished when its current = the Nexus target. Where we have not decided how a point migrates, the target slot is a red ? — a gap to fill, not an answer.

Migration = align the logical model, not the bytes. Adopting the end-state means matching its keys / structure / associations (session-id · flat /sessions/ · owner · DT_LINKs) — not reformatting content (nexus VFS stores opaque bytes) and not assuming nexus at runtime (the FsBackend abstraction makes nexus a backend swap; standalone still runs on local FS).
reference CC — the model we map from done built & matches target partial built but differs / incomplete gap not built here (CC has it) dup redundant copy of the engine's data → collapse to a view open? design question (hover) n/a doesn't apply ? migration undecided — a gap to fill

Badges compare each system to the target, per row. gap — this system lacks a capability CC has / the end-state needs; on the burndown it advances gap → partial → done (what's missing is the left side of that cell). dup — it keeps its own copy of data the engine (scode's session jsonl, ultimately the nexus /sessions/ SSOT) already owns; "merge long-term" = that copy collapses into a view over the one SSOT — one store, not two. Example: sudowork's messages table is a full duplicate of the engine transcript → becomes a view (see the Migration row).

Dependency direction (not a storage row — the rule that keeps the above honest). sudocode → nexus for VFS syscalls (KernelAbi sys_read/write/watch) and for services (A2A write; spawn-child via MAS::start_session). nexus → sudocode only through the SpawnTask<K> DI trait — sudocode-host registers a concrete adapter at boot; one vtable dispatch per session start, no compile-edge reversal. Self lifecycle state: sudocode reports up via a state_callback closure; ManagedAgentService (which owns AgentRegistry) writes the FSM transition — the kernel owns its task table, like a process not editing its own task_struct. Confirmed on sudocode origin/main v0.1.15: no AgentRegistry / ManagedAgentService type refs in sudocode; only KernelAbi + AgentDescriptor. CLI still runs StdFsBackend (seam dormant).
Nexus workspace decisions (rev4 reply, folded in here — verified against nexus-vfs: tip 162225a0c, on_terminate slot registry.rs:326, gate _zone_id bug dispatch.rs:144 all confirmed). Layout = content-type-first zones, each top-level dir a federation zone = access boundary: /repos/{owner}/{repo}/ · /knowledge/{org}/{topic}/ · /skills/ · /tools/ · /sessions/{agent-name}/{sid}/ · /scratch/{session-id}/. Workspace layout is a sudowork convention; nexus only provides primitives. 3-layer lifecycle: agent-name (persistent — repo worktree, avoids re-checkout) · session-id (cross-pid, --resume) · pid (one process; /proc/{pid}/workspace/{alias} DT_LINK, reaped on exit). Access = zone-level zone_perms:[(zone,"rw"|"r")] — not per-path; workspace ≠ fence (sandbox via OS seccomp/namespace). Cleanup: sudowork consumes on_terminate + sys_rmdir for ephemeral GC; DT_LINK has no refcount (symlink semantics, owner = agent-name). sudowork to build (design-ready, no new nexus primitive): the zone layout · per-pid DT_LINK wiring · on_terminate GC · zone_perms adoption. nexus committed (non-blocking): Rust glob/grep search-plugin; path-aware gate fix. Open questions (for consensus)

Q1 Session identity & path — RESOLVED (nexus, 2026-08). Axis B (identity): session-id ≠ pid — three IDs: agent-name (durable principal) · session-id (durable UUID, --resume key, spans N pids) · pid (ephemeral runtime handle). §2.3 had borrowed "session_id" to name the pid handle; fix = start_session_v1 takes an optional session_id (resume) and returns {session_id, pid, workspace_path}; addressing fields renamed to pid. Axis A (path): flat /sessions/<session-id> is the byte SSOT (no workspace_hash, no agent-name nesting); an owner field drives default policy; all associations are DT_LINKs (agent→sessions, session→repo 0..N, pid→session). Isolation = policy (soft), not path — MetaStore has only get/list, so a DT_LINK dir-index reuses native list(prefix) = O(subset) vs building an attribute index. Landed as nexus #4564 (nexus-integration-architecture §2.1/§2.3, merged to develop); the two end-state cells above are updated to match.
Q2 Memory build-out. Which of the 5 missing memory features (extractMemories · session-memory · team-memory · auto-dream · daily-logs) does scode build, and in what order? And where does project-memory live when a workspace DT_LINKs several repos — at the primary mount root (≈ launch path)? (the 5 red ? in the Memory rows resolve here)
Q3 Cross-agent session search via DT_LINK /agents/{name}/sessions/ → shared /agents/sessions/ index? (depends on Q1 session-path + Q6; and on the nexus search-plugin — Rust glob/grep port committed, Python search service today)
Q4 Oversized tool-output offload (CC's tool-results/ + content-replacement) into scode — adopt? Path under /sessions/<sid>/tool-results/? (the red ? in the Tool-output row resolves here)
Q5 Subagent parity. (a) Persist a per-subagent jsonl transcript (CC's agent-<id>.jsonl+.meta.json) vs today's md/json artifacts? (b) Keep subagent-fork at cache-prefix, or make it full-transcript like session --fork? (c) Move subagents to nexus-managed pids (sudocode → MAS::start_session)? (the 2 red ? in the Subagent rows resolve here)
Q6 Workspace & DT_LINK — RESOLVED (nexus rev4). Case A (link to a federation-mounted target resolves cross-node for free) verified. Case B (owner-discovery for a target on a node with no local mount) declined on structural grounds: ZoneMetaStore.last_writer_address is the owner SSOT; a separate path→owner registry = shadow SSOT + DRY violation + leaks federation topology into the kernel. Decision: constrain workspace/link targets to federation-mounted paths — ships today, zero new primitive. See the decisions callout above.
Q7 Standalone resume pointer. Adopt CC's bridge-pointer.json (mtime-heartbeat + cross-worktree-freshest) for the offline scode case? (AgentRegistry is SSOT when nexus is present; standalone has no stored pointer today.) (the red ? in the Resume row resolves here)
Q8 Migration sequencing. Order of: (a) wire scode's dormant KernelFsBackend seam (flat .scode/sessions/ → flat /sessions/<sid>/); (b) collapse sudowork messages → a view over the engine JSONL keyed by acpSessionId; (c) build the missing memory features. Which first?
Q9 sudowork adoption of the nexus workspace/identity model. sudowork today has only conversation-id (SQLite) + extra.workspace — no agent-name identity, no zones, no image/runtime split. rev4 makes the workspace layout a sudowork convention, so this is ours to decide: (a) introduce the persistent agent-name layer — does a sudowork conversation map to a session-id, and what is agent-name (the CLI agent profile? the account/user?)? (b) adopt the content-type-first zones (/repos · /knowledge · /skills · /tools · /sessions · /scratch) — which day 1? (c) reconcile zone-level zone_perms with sudowork's current per-user_id SQLite access (esp. multi-user WebUI + IM channels); (d) on_terminate GC policy — what does sudowork sys_rmdir on pid exit (/scratch only, or more)?
