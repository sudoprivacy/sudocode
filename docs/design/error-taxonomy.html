0一句话

错误不该按"要不要重试"两分,而该按 谁能修 四分。这决定了系统对它做什么。

Transport

传输层自己能修
  • 429 / 5xx / 520·522·524·525
  • connect / timeout
  • 截断的流
自动 retry

Model

LLM 能修
  • 坏的 tool 参数
  • 模型构造的非法请求
  • context 溢出(可 compact 时)
llm-revisit 回喂给模型

Human

人能修
  • 认证失败 401/403
  • 配置错 / 缺 key
  • 请求体过大
报给用户

Fatal

没人能修
  • 服务器返回坏数据
  • 不可恢复的内部错误
真 fatal · 停

4taxonomy 不能干净落地的 3 处(诚实标注)

4 桶是对的轴,但现实有 3 处 resist,重构必须显式处理、不能假装。

① context-window 是状态依赖的。 它先是 Model(自动 compact + retry),compact 次数耗尽后才变 Human。桶取决于运行时状态 → action() 必须结合 compaction 预算计算,不能把桶写死进错误类型。
② llm-revisit 目前只覆盖 tool 错误。 provider 错误从不走回喂模型这条路。要让 Model-可行动的 provider 错误也进 llm-revisit,是 Phase 2 的活。
③ Human vs Fatal 现在根本没被表示。 safe_failure_class 是给 telemetry 的分析轴,不是"谁能行动"的行为轴。两轴要分开(SRP),不能混用。

6守则(重构全程红线)

基础设施不碰 nexus kernel / syscall / raft ABI —— 全在 api/runtime/engine 的错误路径,零 infra-ABI 面
持久化错误是 ephemeral,不持久化任何东西
删除被替换的重复函数 / marker 直接删,callers 重指;不留"replacement for the retired X"墓碑
Perfaction() 是 inline enum match,只在出错时走,成功路径零开销
SRP / 正交行为轴(ErrorAction)与分析轴(safe_failure_class)分开,互不混用
验证每阶段 fmt + clippy 干净,全 CI 绿才 merge
