Agent Context / Image / Profile — Unified Storage Matrix

Map Claude Code's on-disk context model onto the agreed Nexus design: agent image, durable session, and runtime presence. Track the implementation in sudocode & sudowork against that target. The given column describes agreed intent; implementation and deployment status need their own evidence.

The frame (read first). Nexus's two namespaces are the given end-state, not an open question — same split an OS makes between an executable on disk and a running process (nexus-integration-architecture §2): image layer = /agents/{name}/ (config.toml · prompts/ · skills/ · memory/ — persistent, Metastore, the addressable identity; its sessions/ is a DT_LINK index into the flat /sessions/ store, not the bytes) vs runtime layer = /proc/{pid}/ (status · agent→link · workspace/ — ephemeral, stamped at start_session, reaped on exit; pid = an ephemeral run handle, not the session id (session-id is the durable layer — Q1)). Native PID allocation is implemented in nexus-vfs #427 (v0.8.7); consumer release and production adoption are tracked in Q1.

Two core identities and persistent object keys (Q1 clarification, 2026-10-13): agent-name identifies the persistent Agent; pid identifies its ephemeral runtime. A session-id identifies an independently stored persistent object, supplies the --resume key, and can span many PIDs. session-id ≠ pid. Shared-daemon session bytes live at /sessions/<sid>/, keyed by session-id alone; ownership and agent/repo associations are separate. Sudocode co-host already writes this layout. Standalone retains a local workspace partition for discovery and resume. The current managed-agent RPC still names its pid field session_id; see Q1 for the distinction between that field and the transcript key.

VFS namespace and runtime ownership. Paths such as /sessions/, /agents/ and /proc/ are addressed through the kernel; deployment mounts and federation determine their routing. The managed-agent service and cluster composition now live in nexus-vfs (Nexus dependency declaration). The cluster includes SESSIONS_BASE = "/sessions" among its replicated prefixes. Nexus's Python vfs_paths.py still has agent-nested session helpers, but the inspected runtime does not use them for session storage; they are not evidence that the active store needs migration. Tenant-zone isolation remains a separate design requirement.

Agent identity, storage and delivery contract

Durable identity and live runtimes. An Agent keeps its identity at /agents/{name}/ across runtime starts and devices. Agent→runtime is one-to-many. Each live runtime has a node-local /proc/{pid}/ whose agent link points to that Agent. The PID contract uses OS PID[.local_id] to distinguish runtimes sharing a host process. A PID is interpreted with its host; publication and removal follow the actual runtime lifetime. Live status distinguishes initialization, available execution, work and awaiting input.

Shared session history and context. Authorized Agent indexes can reference the same SID, and several runtimes can append its durable history. Messages retain stable identities, parent relationships and tool-call associations. Each runtime continues its selected context chain. A new runtime inherits the most recently completed turn. Its inherited prefix is frozen. A sibling's running turn, tool calls and later results remain in that sibling's branch. Opening another runtime neither replays those calls nor generates an interrupted result for an executing sibling. Compaction changes that context's view while preserving the other continuations and their referenced content. Continuation selection follows committed history order; idle metadata writes preserve that selection. The implementation and acceptance tasks describe the shared runtime layer and host adoption.

Tool identity and retained output. A tool invocation is identified by its originating assistant message ID and the provider's call ID. Results, recovery and completion delivery carry that association across providers. Full outputs use opaque IDs scoped to the same invocation. A persisted fork publishes its transcript after its inherited full outputs are readable through the fork's storage backend.

Transparent AgentHome. Cohost and standalone expose the same Agent identity, logical paths, durable formats, links and attachment recovery semantics. The storage backend handles physical directories, mount placement and transport. A caller reads the same logical Agent data through either host.

Following a link requires access to the target's zone. The transcript and reader registers have one canonical backing location.

Delivery while offline. An authorized sender can persist a message when the recipient has zero runtimes, including before its first start. The next receiver finds unread conversations through its Agent index and feeds the messages into its A2A queue. Send success means durable storage accepted the message. The engine acknowledges consumption after a persisted turn or an explicit user cancellation. Process-local queues and delivery receipts remain transient; shutdown preserves interrupted work as unread. A crash between turn persistence and cursor commit permits replay: delivery is at-least-once, and application effects require their own idempotency.

Discovery, execution and visibility. Listing /agents/ discovers identities visible through mounted zones. Runtime presence comes from the live process registry. Zone authorization defines the replication set for private Agent data, discovery and participant conversations. An authorized provisioning service creates a shared conversation and each private index within its proper zone. Sender identity is established by the transport contract; access and node membership follow the service and credential boundaries.

Move and recovery. An Agent's durable closure consists of its home and the canonical content referenced by its indexes and attachments. Move preserves the identity and link relationships. Content completion verifies the required bytes at the destination with the source offline. Runtime handoff establishes the new execution and consumption role before it continues work. The shared runtime service contract owns installation, connection and lifecycle across devices.

A template is not an agent

This matrix is about agents, and until the sudowork frontend was looked at there seemed to be only agents. There is a second thing above them, and conflating the two is how one agent ended up owning several people’s memory.

A template — 「招聘专家」, 科研申报, the entries behind /api/agents/hub/list — is a shared, organization-level definition: prompts, bound skills, a display name. It is keyed by its catalog id and is the same object for everybody who picks it.

An agent is the durable principal this matrix describes: it owns a home at /agents/{name}/, its memory, its conversations and its inbox, and it outlives any session or pid. It belongs to exactly one person.

So a template cannot be an agent. A shared definition cannot own one person’s memory. Two users who both pick 「招聘专家」 chose the same template and are not the same principal. Moss used to hand the template’s name to start_session as the agent_id; because /agents/{name}/ is zone-wide and a zone is a tenant, every user in an organization who picked it landed in one agent home, sharing its state stream, conversation list and mailbox (moss #314).

The agent is therefore the pair — this user, that template — and a session with no template at all belongs to the user’s own agent rather than to nobody (moss #308).

Where the concept lives, by design:

  • nexus-vfs and sudocode have no notion of a template, and should not: they know agents (agent_id, AgentDescriptor { name }). Verified — zero occurrences in either managed_agent.
  • moss holds both and now keeps them apart: assistantName is the template reference (catalog lookup, shared-memory directory, display name, wiki/corp-app scopes), while what nexus is told is the per-user instance.
  • sudowork’s UI does not yet make the distinction. The 「智能体库」 lists templates and 「我的智能体」 lists installed templates; there is no word for an instance, and no way to create one. That is the open end, not a storage question — see below.

The consequence that is still open. A user has exactly one agent of their own plus one per template they pick. There is no way to create a second agent of one’s own, so every conversation a user starts without choosing a template accumulates into a single memory bucket that cannot be partitioned. The architecture already allows more (「一个人可以有多个 copilot」); the creation path was never designed, because the discussion was about which button is primary rather than about which objects exist.
